## 1. Security Posture

### CRITICAL

- **[SEC-AWS-IAM-002#1] IAM assume role policy with wildcard Principal** — `01_broken_access_control.tf:61` | Blast: infrastructure-wide | CIS: CIS AWS 1.16 | Effort: Small | Status: VERIFIED
  Description: `aws_iam_role.anyone` uses `Principal = "*"` in its assume-role policy, meaning any entity in any AWS account worldwide can call `sts:AssumeRole` against it without restriction. This is the IAM equivalent of leaving an SSH key with no passphrase on a public server. An attacker needs only the role ARN (easily discoverable via account enumeration) to assume it and inherit all attached policies.
  Recommendation: Replace `"Principal": "*"` with the specific ARN(s) of trusted entities — e.g., `{"Service": "lambda.amazonaws.com"}` for Lambda, or `{"AWS": "arn:aws:iam::123456789012:role/trusted-role"}` for cross-account. If cross-account trust is intentional, add an `aws:PrincipalOrgID` condition to restrict it to the organisation.
  Verification: Run `aws iam get-role --role-name demo-anyone-role` and confirm `AssumeRolePolicyDocument` has no `"Principal": "*"` without a restrictive `Condition` block.

- **[SEC-AWS-SG-001#1] Security group allows SSH ingress from 0.0.0.0/0 (CRITICAL escalation: port 22)** — `05_security_misconfiguration.tf:34` | Blast: environment | CIS: CIS AWS 5.2 | Effort: Small | Status: VERIFIED
  Description: `aws_security_group.ssh_open` has an ingress rule on TCP/22 with `cidr_blocks = ["0.0.0.0/0"]`, exposing SSH to the entire internet. The SEC-AWS-SG-001 escalation condition fires because port 22 (SSH) is in scope. This security group is also attached to `aws_instance.public` in the same file, giving the internet direct SSH access to an EC2 instance with a public IP address. This is one of the most commonly exploited misconfigurations across AWS deployments.
  Recommendation: Remove the 0.0.0.0/0 ingress rule entirely and use AWS Systems Manager Session Manager for shell access (no inbound port required). If SSH is truly needed, restrict `cidr_blocks` to a specific bastion or VPN CIDR.
  Verification: Run `aws ec2 describe-security-groups --group-ids <sg-id>` and confirm no ingress rule has `0.0.0.0/0` as source for port 22.

### HIGH

- **[SEC-AWS-IAM-001#1] IAM policy with wildcard resource** — `01_broken_access_control.tf:38` | Blast: infrastructure-wide | CIS: CIS AWS 1.16 | Effort: Medium | Status: VERIFIED
  Description: `data "aws_iam_policy_document" "all_access"` has `actions = ["*"]` and `resources = ["*"]`, which is attached to `aws_iam_policy.godmode`. Any principal that holds this policy can perform every API action on every resource in the AWS account, including reading Secrets Manager, creating IAM users, and exfiltrating all S3 objects.
  Recommendation: Replace `actions = ["*"]` and `resources = ["*"]` with the minimum set of actions and the specific ARN(s) the policy needs. Use IAM Access Analyzer to derive a least-privilege policy from actual CloudTrail activity.
  Verification: Run `terraform plan` and verify the rendered policy document contains no `"Action": "*"` or `"Resource": "*"` statements.

- **[SEC-AWS-IAM-001#2] IAM user inline policy with wildcard resource** — `07_identification_auth.tf:46` | Blast: infrastructure-wide | CIS: CIS AWS 1.16 | Effort: Medium | Status: VERIFIED
  Description: `aws_iam_user_policy.human_admin` grants `Action = "*"` and `Resource = "*"` to the `demo-human` IAM user, which also has a long-lived access key (SEC-AWS-ACCESSKEY-001 below). Together, a leaked access key gives an attacker full administrative control of the account. This combination was the root cause of several large AWS breaches.
  Recommendation: Remove the wildcard policy; scope to the minimum actions the user requires. Better still, replace the IAM user with SSO + role assumption so no long-lived credential exists.
  Verification: Run `aws iam list-user-policies --user-name demo-human` and `aws iam get-user-policy --user-name demo-human --policy-name demo-human-admin` to confirm no wildcard statements remain.

- **[SEC-AWS-ACCESSKEY-001#1] Long-lived IAM access key created for a human user** — `07_identification_auth.tf:36` | Blast: module | CIS: CIS AWS 1.4 | Effort: Medium | Status: VERIFIED
  Description: `aws_iam_access_key.human` provisions a permanent AKID/secret for `aws_iam_user.human`. Long-lived keys are exfiltrated via developer workstations, CI logs, git history, and EC2 instance backups. Unlike STS tokens (which expire in hours), a leaked AKID is valid until manually rotated. Combined with the wildcard inline policy above, this key grants full account access.
  Recommendation: Replace the IAM user with an IdP-federated SSO identity or OIDC-based role for CI/CD. If a key is unavoidable, enforce 90-day rotation via automation, store the secret in AWS Secrets Manager, and restrict the attached policy to the minimum required actions.
  Verification: Run `aws iam list-access-keys --user-name demo-human` and confirm no keys exist, or that key `CreateDate` is within 90 days.

- **[SEC-AWS-SSRF-001#1] EC2 instance with IMDSv1 enabled (missing metadata_options block)** — `03_injection.tf:37` | Blast: single-resource | CIS: CIS AWS 5.6 | Effort: Small | Status: VERIFIED
  Description: `aws_instance.ec2_user_data_injection` has no `metadata_options` block, so IMDSv1 is active by default. This is structurally identical to the Capital One breach (2019, 100M records).

An attacker who exploits any web application on this instance can trivially exfiltrate IAM credentials.

## 2. DRY and Code Reuse

Each of the ten OWASP category files is self-contained with no shared modules or locals. This is appropriate for a corpus whose purpose is demonstration, but several patterns repeat across files:

- Three separate `aws_db_instance` resources (`02`, `05`, `08`) share the same basic schema. A production codebase would extract these into a module.
- Four `aws_s3_bucket` resources (across `01`, `02`, `08`, `09`) are all standalone; a shared module with opinionated versioning + encryption defaults would prevent these findings at authoring time.
- The IMDSv1 pattern (`aws_instance` without `metadata_options`) recurs in five places across four files.

No DRY-violation findings are raised for this intentionally fragmented corpus, but the repetition illustrates how a shared module with secure defaults would have prevented the bulk of the HIGH findings.

## 9. Stack-Specific Findings

### EXPLORATORY — Hardcoded API key in locals

- **[EXPLORATORY-CREDENTIAL#1] Hardcoded API key (`sk-live-` pattern) in locals** — `04_insecure_design.tf:37` | Blast: infrastructure-wide | CIS: n/a | Effort: Small | Status: SPECULATIVE
  Description: `locals { api_key = "sk-live-AAAAAAA..." }` contains a hardcoded secret. Even in a demo corpus, committing this pattern to any git repository permanently embeds the secret in history. The detector did not fire a catalog rule on this pattern (credential pattern detection for `sk-live-` is documented as a roadmap item in `versions.tf`). Real `sk-live-` keys for payment or AI APIs would be live credentials at the moment of the first push.
  Recommendation: Remove the hardcoded value; fetch from AWS Secrets Manager or SSM Parameter Store at runtime. Add `gitleaks` or `detect-secrets` to pre-commit hooks.

### EXPLORATORY — Shared Lambda IAM role with AdministratorAccess

- **[EXPLORATORY-IAM#1] Single IAM role with AdministratorAccess shared across all Lambda functions** — `04_insecure_design.tf:41` | Blast: infrastructure-wide | CIS: n/a | Effort: Large | Status: SPECULATIVE
