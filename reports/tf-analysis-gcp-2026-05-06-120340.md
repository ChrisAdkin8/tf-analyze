## 1. Security Posture

### CRITICAL

- **[SEC-GCP-IAM-002#1] Public IAM binding on storage bucket** — `01_broken_access_control.tf:38` | Blast: infrastructure-wide | CIS: 5.1 | Effort: Small | Status: VERIFIED
  Description: `google_storage_bucket_iam_member.public_objects` grants `roles/storage.objectViewer` to `allUsers`, making every object in `demo-public-bucket` anonymously readable from the internet. This is the most-exploited GCS misconfiguration — attackers actively scan for public buckets.
  Recommendation: Remove the `allUsers` binding. If external read access is genuinely required, use signed URLs with short TTLs (`gcloud storage sign-url`).
  Verification: `gcloud storage buckets get-iam-policy gs://demo-public-bucket --format='value(bindings)' | grep allUsers` returns nothing.

- **[SEC-GCP-NETWORK-001#1] SSH open to 0.0.0.0/0** — `05_security_misconfiguration.tf:62` | Blast: environment | CIS: 3.6 | Effort: Small | Status: VERIFIED
  Description: `google_compute_firewall.ssh_open` allows `tcp:22` from `0.0.0.0/0`. Any internet host can attempt authentication against every VM in the `default` network. This is the #1 attacked surface on GCP and leads to credential-spray and crypto-mining campaigns within minutes of exposure.
  Recommendation: Restrict `source_ranges` to the internal VPC CIDR or the corporate IP range. For operator access, require IAP-tunnelled SSH (`gcloud compute ssh --tunnel-through-iap`) and remove the firewall rule entirely.
  Verification: `gcloud compute firewall-rules describe demo-ssh-open --format='value(sourceRanges)'` must not include `0.0.0.0/0`.

### HIGH

- **[SEC-GCP-IAM-001#1] Project-level binding of `roles/owner`** — `01_broken_access_control.tf:32` | Blast: infrastructure-wide | CIS: 1.6 | Effort: Medium | Status: VERIFIED
  Description: `roles/owner` grants the ability to delete the project, modify audit logs, and assume any SA. Granting this to a user identity at project scope is CIS GCP 1.6 non-compliant.
  Recommendation: Remove the `roles/owner` binding. Grant only the specific roles the user needs (e.g., `roles/storage.admin` if the intent is bucket management).

- **[SEC-GCP-IAM-003#1] Member bound at both project and resource scope** — `01_broken_access_control.tf:45` | Blast: module | CIS: n/a | Effort: Small | Status: VERIFIED
  Description: `serviceAccount:app@demo-project.iam.gserviceaccount.com` holds `roles/storage.objectViewer` at both project scope (`google_project_iam_member.app_at_project`) and resource scope (`google_storage_bucket_iam_member.app_at_bucket`). The project-level grant silently supersedes the resource-level one, defeating the apparent narrowing.
  Recommendation: Remove `google_project_iam_member.app_at_project`; keep only the resource-level binding.

- **[SEC-GCP-LOGGING-001#1] Cloud Audit Logs not configured** — `examples/terragoat/gcp` (corpus-level) | Blast: infrastructure-wide | CIS: 2.1 | Effort: Medium | Status: VERIFIED
  Description: No `google_project_iam_audit_config` resource exists in the corpus. Without it, `DATA_READ` and `DATA_WRITE` audit events are not collected for any GCP API. Post-incident forensics is impossible.
  Recommendation: Add a `google_project_iam_audit_config` covering `allServices` with `DATA_READ`, `DATA_WRITE`, and `ADMIN_READ` log types.

- **[SEC-SENSITIVE-001#1] Sensitive output not marked sensitive** — `02_cryptographic_failures.tf:77` | Blast: single-resource | CIS: n/a | Effort: Small | Status: VERIFIED
  Description: `output.vault_token_echo` forwards `var.vault_token` (which IS marked `sensitive = true`) but the output itself has no `sensitive = true`. The value appears in plaintext in `terraform plan`, `terraform output`, and CI logs.
  Recommendation: Add `sensitive = true` to the output block.

- **[SEC-GCP-COMPUTE-SA-001#1] Compute instance uses default Compute SA** — `05_security_misconfiguration.tf:40` | Blast: module | CIS: 4.1 | Effort: Small | Status: VERIFIED
  Description: `google_compute_instance.exposed` omits `service_account {}`, defaulting to the project's Compute Engine default SA which holds `roles/editor` project-wide. Any code running on this VM can modify most project resources.
  Recommendation: Attach a dedicated, least-privilege SA via a `service_account { email = google_service_account.vm.email scopes = ["cloud-platform"] }` block.

- **[SEC-GCP-COMPUTE-PUBLIC-IP-001#1] VM has public IP via `access_config`** — `05_security_misconfiguration.tf:40` | Blast: single-resource | CIS: 4.8 | Effort: Small | Status: VERIFIED
  Description: `network_interface { access_config {} }` assigns an ephemeral public IP. Combined with the open-SSH firewall rule, this VM is reachable from the entire internet on port 22.
  Recommendation: Remove the `access_config {}` block and use IAP for operator access.

- **[SEC-GCP-SQL-PUBLIC-001#1] Cloud SQL has public IPv4** — `05_security_misconfiguration.tf:75` | Blast: module | CIS: 6.1.1 | Effort: Small | Status: VERIFIED
  Description: `google_sql_database_instance.main` sets `ip_configuration { ipv4_enabled = true }`. The database has a public IP; any host with network path can attempt authentication.
  Recommendation: Set `ipv4_enabled = false` and use Private Service Connect or Cloud SQL Auth Proxy.

- **[SEC-GCP-SQL-PUBLIC-001#2] Cloud SQL has public IPv4 (SSRF)** — `10_ssrf.tf:42` | Blast: module | CIS: 6.1.1 | Effort: Small | Status: VERIFIED
  Description: `google_sql_database_instance.public_db` also has `ipv4_enabled = true`. Even with an `authorized_networks` entry for the office CIDR, a workload with free egress (the SSRF scenario) can reach this endpoint.
  Recommendation: Same as above — disable public IP and use Cloud SQL Auth Proxy.

- **[SEC-GCP-BUCKET-001#1] GCS bucket missing `public_access_prevention`** — `05_security_misconfiguration.tf:97` | Blast: single-resource | CIS: 5.1 | Effort: Small | Status: VERIFIED
  Description: `google_storage_bucket.prod_data` has neither `public_access_prevention = "enforced"` nor `uniform_bucket_level_access = true`. Legacy ACLs can inadvertently grant anonymous access.
  Recommendation: Add `public_access_prevention = "enforced"` and `uniform_bucket_level_access = true`.

- **[SEC-GCP-BUCKET-001#2] Audit log target bucket missing `public_access_prevention`** — `09_logging_monitoring.tf:55` | Blast: single-resource | CIS: 5.1 | Effort: Small | Status: VERIFIED
  Description: `google_storage_bucket.audit_target` receives access logs from `google_storage_bucket.logged_source` but has no `public_access_prevention`. An attacker who can read the audit bucket learns access patterns without touching the source bucket.
  Recommendation: Add `public_access_prevention = "enforced"` to the audit target bucket.

- **[SEC-DATASOURCE-001#1] `data.external` executes at plan time** — `03_injection.tf:50` | Blast: module | CIS: n/a | Effort: Medium | Status: NEEDS-REVIEW

## 9. Stack-Specific Findings

### GKE (`google_container_cluster.demo` in `07_identification_auth.tf:35`)

#### Catalogue findings (HIGH)

- **[SEC-GCP-GKE-NETWORK-POLICY-001#1] Network policy disabled** — `07_identification_auth.tf:34` | CIS: 8.4.1 | Effort: Small | Status: VERIFIED
  Description: `network_policy {}` block is absent from the cluster. Without it, any pod in the cluster can reach any other pod or external endpoint — a compromised pod can pivot freely.
  Recommendation: Add `network_policy { enabled = true provider = "CALICO" }` to the cluster block.

- **[STK-GCP-GKE-002#1] Workload Identity not enabled** — `07_identification_auth.tf:34` | CIS: 8.5.2 | Effort: Medium | Status: VERIFIED
  Description: `workload_identity_config {}` is absent. Pods must use service-account JSON key files to authenticate to GCP APIs — long-lived credentials that survive pod restarts, ship in etcd backups, and are hard to rotate.
  Recommendation: Add `workload_identity_config { workload_pool = "${var.project}.svc.id.goog" }` and annotate Kubernetes SAs to bind to GCP SAs.

- **[STK-GCP-GKE-NODEPOOL-001#1] Node pool missing shielded-instance config** — `07_identification_auth.tf:45` | CIS: 8.4.2 | Effort: Small | Status: VERIFIED
  Description: `google_container_node_pool.default` has no `shielded_instance_config {}` block. Secure boot and integrity monitoring are both off — kernel-level rootkits can persist across cordons and node-pool upgrades.
  Recommendation: Add to `node_config`: `shielded_instance_config { enable_secure_boot = true enable_integrity_monitoring = true }`.

#### EXPLORATORY GKE findings (CIS gaps not yet in catalogue)

- **[EXPLORATORY] Private nodes disabled** — `07_identification_auth.tf:35` | CIS: 8.5.3
  `enable_private_nodes = false` (default). Node VMs have public IPs — direct internet exposure. Fix: add `private_cluster_config { enable_private_nodes = true master_ipv4_cidr_block = "172.16.0.0/28" }`.

- **[EXPLORATORY] Master authorized networks not configured** — `07_identification_auth.tf:35` | CIS: 8.5.4
  No `master_authorized_networks_config {}` block. The Kubernetes API server is reachable from any IP. Fix: restrict to operator/CI CIDR ranges.

- **[EXPLORATORY] Application-layer Secrets Encryption disabled** — `07_identification_auth.tf:35` | CIS: 8.5.5
  No `database_encryption { state = "ENCRYPTED" key_name = "..." }` block. Kubernetes Secrets are stored unencrypted in etcd at the cluster level.

### Cloud SQL

#### EXPLORATORY (not yet in catalogue)

### KMS

- **[STK-GCP-KMS-001#1] KMS key missing rotation period** — `02_cryptographic_failures.tf:37` | CIS: 1.10 | Effort: Small | Status: VERIFIED
  Description: `google_kms_crypto_key.data` has no `rotation_period`. Compromise of the key material remains valid indefinitely.
  Recommendation: Add `rotation_period = "7776000s"` (90 days).

- **[STK-GCP-KMS-LOCATION-001#1] CMEK consumer in different region from key ring** — `02_cryptographic_failures.tf:50` | CIS: n/a | Effort: Medium | Status: VERIFIED
  Description: `google_storage_bucket.encrypted_cross_region` is in `us-central1` but its KMS key ring is in `us-east1`. Cross-region CMEK violates data-residency guarantees and doubles encryption egress costs.
  Recommendation: Co-locate the bucket and key ring in the same region.

### Provisioner / Injection

- **[SEC-PROVISIONER-001#1] `null_resource` with `local-exec` provisioner** — `03_injection.tf:40` | CIS: n/a | Effort: Medium | Status: NEEDS-REVIEW
